# Audit round 3 — findings and fixes

Audit date: 2026-08-06

Branch: `master` at `30c3b44`

Follow-up to [`docs/report.md`](../report.md) (2026-07-28) and
[`remediation-plan.md`](remediation-plan.md) (2026-08-04). Scope was the code that
had never been audited — the `solana-relayer` crate and the `solana-gate`
changes introduced by `30c3b44`, plus the whole React frontend, which the
previous rounds only ever inspected by reading.

Eight findings from the source audit, all fixed, each with a regression test that
fails before the fix. A further **nine** were then found only by deploying to
live testnets (Ethereum Sepolia + Hoodi) — see the addendum. Every one of those
was invisible to the local anvil suite, and five of them made the stack
non-functional or insecure on a real chain while every existing test stayed green.

| Sev | ID | Component | Summary |
| --- | --- | --- | --- |
| **HIGH** | R-1 | `solana-gate` | Unbounded signature array in `verify_threshold` — a compute-budget bomb that permanently bricks `claim`, `cancel` **and** `refund` for a submission |
| **HIGH** | R-2 | `solana-relayer` | Forwards every stored signature, including non-validators', and requests no compute budget — the delivery half of R-1 |
| **HIGH** | R-3 | `frontend` | The shipped frontend does not compile: `SOLANA_CHAIN_ID` is exported twice |
| **MED** | R-4 | `solana-relayer` | The source scanner's cursor jumps past unscanned history whenever the backlog exceeds `max_batch` |
| **MED** | R-5 | `frontend` | No chain-id binding on wallet writes — a stale `chainId` sends `approve`/`send`/`swap`/`finalize` to a different chain |
| **MED** | R-6 | `frontend` | Token decimals are held from the *previous* token while a new read is in flight, so a submit can encode 10^Δ times the intended amount |

| **LOW** | R-8 | `frontend` | `Dropdown` displayed the first option as selected when the parent's value matched none of them |

Two smaller robustness fixes were made alongside: an unmapped submission status
rendered a blank badge, and an unknown submissionId rendered an empty detail

## HIGH R-1 — a padded signature array bricks every path that spends validator authority

**Evidence:** `crates/solana-gate/src/lib.rs:761` (pre-fix).

`verify_threshold` looped over every signature supplied, calling
`secp256k1_recover` on each. That syscall costs roughly **25k compute units**,
against a **200k** default per-instruction budget — so eight signatures exhaust
the budget before quorum is even counted.

The array is attacker-controllable. The signature store authenticates a
signature against its *claimed signer*; it does not know the validator set (this
is the same property that made H-1 reachable), and `bridge-db` places no cap on
how many signature rows a submission may accumulate. Anyone holding a
`Sign`-scoped token can therefore append valid-but-unregistered signatures from
throwaway keys to a pending submission.

`claim`, `cancel` and `refund` all funnel through this one verifier. Padding the
array does not merely delay the payout — it takes **both recovery paths down with
it**, which is the difference between a stuck transfer and a lost one.
`Gate.sol` has carried the equivalent cap since `16ed706`
(`TooManySignatures`, `Gate.sol:608`); the Solana gate had no counterpart.

**Fix:** reject `signatures.len() > cfg.validators.len()` before the first
recover. A correct array can never be longer — signers must be distinct and
strictly ascending — so the check costs an honest relayer nothing and makes the
refusal cheap. New `GateError::TooManySignatures`, appended so existing
discriminants do not shift.

**Tests:**

- `c1_tests::more_signatures_than_validators_is_refused`
- `c1_tests::junk_padding_cannot_force_the_expensive_path`
- `c1_tests::an_array_no_longer_than_the_validator_set_passes_the_cap`
- `c1_tests::claim_cancel_and_refund_share_the_cap`
- `c1_tests::error_discriminants_are_append_only`
- `account_level::a_padded_cancel_is_refused_on_length_and_burns_nothing`
- `account_level::a_heavily_padded_array_never_reaches_the_recover_loop`
- `account_level::an_array_within_the_validator_count_still_reaches_verification`

The account-level three drive the real handler in a `solana-program-test` bank
and assert the marker PDA is untouched, so a refused attempt leaves the transfer
claimable.

## HIGH R-2 — the relayer forwards junk and asks for no compute budget

**Evidence:** `crates/solana-relayer/src/target.rs:193` (pre-fix).

The delivery half of R-1. The module header claimed "we cap the array at the
count the config declares", but the code passed `raw_sigs.len()` as the cap —
which is not a cap at all. Every signature that merely *recovers* was forwarded,
registered validator or not.

The transaction also requested no compute budget, leaving it on the 200k default.
The remediation plan flagged this as unmeasured: a legitimate 5-of-7 gate spends
~175k CU on recovery alone, before keccak, Borsh and the SPL transfer.

**Fix:** read the canonical config PDA and keep only signatures that recover to a
registered validator, capped at the validator count; skip submission entirely
below threshold rather than burning fees on a guaranteed revert; and request a
budget scaled to the validator set (`compute_budget_for`), clamped to Solana's
1.4M per-transaction maximum. The config is hand-decoded from Borsh because
`solana-gate` sits outside this workspace with its own (deliberately v3)
lockfile — so the layout is pinned by a test.

**Tests:** `target::tests::signatures_from_non_validators_never_reach_the_gate`,
`the_array_is_capped_at_the_validator_count`, `config_layout_matches_the_program`,
`a_truncated_config_is_an_error_not_an_empty_validator_set`,
`the_compute_budget_scales_with_the_validator_set`.

The truncated-config test matters on its own: a malformed account decoding as an
*empty* validator set would filter every signature away and look exactly like
"nobody has signed yet", hiding the fault indefinitely.

## HIGH R-3 — the shipped frontend does not compile

**Evidence:** `frontend/src/data/format.ts:6` and `:106` (pre-fix).

`SOLANA_CHAIN_ID` was exported twice. `bun run build` (`tsc -b && vite build`)
fails with four errors, so the frontend in `30c3b44` cannot be built at all.

Every Rust and Solidity suite stayed green through this, and CI had no frontend
test step beyond a build that nobody had run since the commit landed.

**Fix:** remove the duplicate. CI now runs `bun run build` *and* the new
Playwright suite, so a non-compiling frontend fails the pipeline.

## MED R-4 — the scanner's cursor advances past unscanned history

**Evidence:** `crates/solana-relayer/src/source.rs:140-212` (pre-fix).

`getSignaturesForAddress` walks **backwards** from the tip and stops at `until`
*or* at `limit`, whichever comes first. With a backlog larger than `max_batch`
(default 100) the call returns the **newest** 100 signatures and silently omits
the older ones sitting immediately above the cursor. The scanner processed that
page oldest-first and set the cursor to its newest entry — permanently skipping
the omitted range. Those `Sent` events are never signed, so the transfers behind
them never reach quorum.

This is finding H-3's "cursor advanced past unhandled logs", one layer down: the
per-log handling was already durable, but the *range* was not.

**Fix:** paginate with `before` until a page comes back short (meaning it reached
the cursor), and only then process a contiguous range. Beyond
`max_batch × 100` signatures of backlog it fails loudly and leaves the cursor
put — falling behind is recoverable, a hole is not. A first run with no cursor
still starts at the tip, which is deliberate rather than a skip. Failed
transactions now also advance the cursor, so they cannot wedge the loop.

**Tests:** `source::tests::a_full_page_means_there_is_more_history_below_it`,
`the_first_run_starts_at_the_tip`,
`an_unwalkable_backlog_fails_instead_of_skipping`. The pagination rule is
extracted into `next_page_action` so it is testable without an RPC.

## MED R-5 — no chain-id binding on wallet writes

**Evidence:** `frontend/src/wallet/eth.ts:270` (pre-fix). Raised as a LOW in the
2026-07-28 report and still open.

`sendTx` sent `{from, to, data}` with no `chainId`, and the UI gated on
`wallet.chainId` — a React snapshot delivered by a `chainChanged` event, which
can lag the wallet and can change while the user is typing an amount or a quote
is in flight.

Contract addresses are not chain-scoped by the wallet. The same address on
another chain is a different contract, or nothing: an `approve` landing on the
wrong chain grants an unknown spender, and a `send` locks funds in something that
will never emit `Sent`.

**Fix:** every write now takes the chain it was built for and applies two
independent guards — re-read `eth_chainId` immediately before signing and refuse
on mismatch (`WrongChainError`), and pass `chainId` in the transaction so the
wallet checks it too. `finalize()` binds to the **destination** chain, not the
transfer's origin.

**Tests:** `unit/eth.spec.ts` — every write refuses on a drifted chain, a
matching chain stamps `chainId` into the transaction, and finalize binds to the
destination. `app/bridge.spec.ts`, `app/bridge-swap.spec.ts` and
`app/swap.spec.ts` drive the same race through the app with a wallet that moves
without emitting `chainChanged`, asserting that **nothing is sent**.

## MED R-6 — stale decimals scale the amount

**Evidence:** `frontend/src/components/BridgeView.tsx:199-224` (pre-fix). Also
raised as a LOW in the first report.

`decimals` is read asynchronously and scales the typed amount into base units.
It kept the previous token's value while a new read was in flight, so switching
from an 18-decimal token to a 6-decimal one and submitting during that window
encodes **10¹²** times the intended amount. `balance` was equally stale, so the
insufficient-balance check validated against the wrong token and let it through.

**Fix:** track which `(chain, token, spender)` triple the reads belong to. Reads
are invalidated at the start of a refresh, `amountBase` is zero while stale, and
the button says "Reading token…" rather than encoding with a value that may
describe a different asset.

**Tests:** `app/bridge.spec.ts` — with the token read stalled, the button refuses
to submit; a token change re-reads balance and allowance.

## LOW R-7 — a second transfer erased the first one's recovery data

**Evidence:** `frontend/src/components/BridgeView.tsx:61` (pre-fix).

The M5 fix persisted the in-flight swap-and-bridge flow under a single
`localStorage` key, with a comment claiming it was "keyed by corridor so distinct
in-flight transfers don't clobber each other". It was not. A second transfer
overwrote the first.

`finalize()` needs values captured from the source chain's `Sent` log —
debridgeId, amount, nonce, the peer router, the swap intent. Nothing else in the
UI can reconstruct them, so the overwritten transfer's bridged stable sits on the
destination router with no way to move it on.

**Fix:** key by submissionId (`bridge.pendingSwap.v2.<id>`), migrate the v1
record on first load, restore the flow that still needs an action, tell the user
how many others are waiting, and clear only the finished transfer's own key.

**Tests:** `app/bridge-swap.spec.ts` — a second transfer leaves both records
intact and the UI reports the other one; finishing one clears only its own key;
corrupt stored state is discarded rather than crashing the view.

## LOW R-8 — the dropdown claimed a selection the form did not hold

**Evidence:** `frontend/src/components/Dropdown.tsx:23` (pre-fix). Raised in the
first report and still open.

`options.find(o => o.value === value) ?? options[0]` meant that typing a custom
token address left the picker confidently displaying the *first registry token*.
The asset named on screen and the asset in the transfer being built were
different.

**Fix:** match only the parent's value; show a placeholder ("Custom address")
otherwise. `aria-haspopup`/`aria-expanded` added while there.

**Tests:** `app/dropdown.spec.ts`.

## Addendum — two defects found by running on a live testnet

Found 2026-08-10 deploying to Ethereum Sepolia and Hoodi. Both live in
`scripts/run.sh`, both are invisible on a local anvil, and together they made the
stack silently non-functional on any real chain: validators never read a single
log, so no transfer could ever be signed.

### L-1 — scanners start at block 0

`run.sh` hardcoded `start_block = 0` for every validator and indexer source.

A fresh anvil begins at height 0, so this is correct locally and catastrophic
anywhere else. Sepolia is past **11.4 million** blocks: scanning from genesis
never reaches the current deployment, and burns the RPC quota trying. Nothing
errors — the stack comes up "healthy" and simply never sees an event.

**Fix:** `START_BLOCK` (a height, or `head` to begin at each chain's tip) plus
`START_BLOCKS[chain_id]` for per-chain overrides. Defaults to `0` when
`LOCAL_ANVIL=true` and `head` otherwise, so the failure mode points at "sees new
events" rather than "silently busy for hours".

### L-2 — `eth_getLogs` range exceeds what hosted RPCs allow

`run.sh` hardcoded `max_block_range = 1000`.

Hosted providers **cap** this and **reject** anything wider rather than
truncating it. On Alchemy's free tier the cap is 10 blocks, so every single scan
returned:

```
HTTP 400 … Under the Free tier plan, you can make eth_getLogs requests with up
to a 10 block range.
```

The validator's retry logic did exactly what it should — rotate endpoint, retry —
producing an endless failure loop at ~2 requests/second with no events ever read.
A local anvil has no such cap, so 1000 always worked in testing.

**Fix:** `MAX_BLOCK_RANGE` config variable, still defaulting to 1000 for local
nodes; the live config sets 10.

### L-3 — polling cadence tuned for anvil exhausts a hosted RPC

`run.sh` hardcoded `poll_interval_ms = 300` (validators) and `500` (indexer).

Against an instant-mining anvil that is right. Against a 12s chain with a
10-block `getLogs` window it re-requests the same range ~40 times per new block —
multiplied by 2 validators × 2 chains, plus the indexer, plus the keeper, all
sharing one key. The result was a permanent `HTTP 429 … exceeded its compute
units per second capacity`, which starved the *other* callers: the swap-pool
query failed 10/10 times purely from contention.

**Fix:** `POLL_INTERVAL_MS` / `INDEXER_POLL_INTERVAL_MS` config variables, still
300/500 by default. The live config uses 8000/10000 — still far faster than a
10-block window can fill. 429s went from constant to zero.

### L-4 — the swap pool's token list scanned from genesis

`crates/graphql-api/src/swap.rs:93,97` filtered `from_block(0)`.

This was a LOW in the 2026-07-28 report ("performs two genesis-to-tip log scans
whenever pool metadata is requested") and had not been fixed. On anvil it is
merely wasteful; on Sepolia the request is **rejected outright** by the block-range
cap, `pools()` swallowed the error into `None`, and the entire Swap view rendered
empty with nothing in the log to explain why.

**Fix, in three parts** — the first was necessary but not sufficient, which is
worth recording because each step only became visible once the previous one
landed:

1. **Bounded + chunked.** `--swap CHAINID=RPC,POOL[,FROM_BLOCK]` carries the
   pool's deploy height; the range is walked in `GRAPHQL_MAX_BLOCK_RANGE` chunks.
   Correct, but still ~150 round trips per query on a cold cache.
2. **Memoised and incremental.** Replayed state is cached per chain and each
   query scans only blocks produced since the last one. Progress persists even
   when a chunk fails, so a backfill behind a rate limit converges instead of
   restarting from the deploy block every time.
3. **Serve partial results.** Listings happen at deployment, so they land in the
   first chunk; failing the whole query because the scan had not yet reached the
   tip blanked the view for ~25 minutes after every restart. A truncated scan now
   returns what it found and logs a warning. The bounded cost is one-directional:
   a token *delisted* in the unscanned tail keeps showing until the backfill
   reaches it.

### L-5 — a delivered transfer was recorded as refund-eligible

**Evidence:** `crates/bridge-db/src/lib.rs` `mark_claimed` / `mark_cancelled` /
`mark_refunded`, all bare `UPDATE … WHERE submission_id = $1`.

The indexer runs **one loop per chain, concurrently**. The destination's
`Claimed` can therefore be observed before the source's `Sent` has created the
row — routinely so during a backfill, where the two chains are scanned at
unrelated speeds. An `UPDATE … WHERE` that matches nothing returns `Ok(())`, so
the claim was silently dropped.

Caught on the live stack with timestamps a third of a second apart:

```
04:33:46.355  indexer: observed Claimed  chain_id=560048  submission_id=0xa667af…
04:33:46.988  submissions row created (status='signed')
```

The transfer was **delivered** — `executed[id] = true` on Hoodi, receiver paid —
yet the row read `status=signed, refund_status=eligible, claim_tx=NULL`. The
refund sweep had flagged a completed transfer as stuck.

Not a fund-safety bug: `cancel` on an executed submission reverts
`AlreadyExecuted`, and the live GraphQL status (which reads the chain) correctly
said `EXECUTED`. But it is a false "stuck" signal that would drive validators to
attest a cancel and the keeper to spend gas on a guaranteed revert, and it
corrupts history permanently.

**Fix:** a `pending_lifecycle` table. A marker whose row does not exist yet is
parked (`park_if_missing`) and applied by `apply_pending_lifecycle` the moment
the row appears — from either writer, `observe_submission` (indexer) or
`upsert_signature` (validator POST), since both can be the one that creates it.

**Verified** by wiping the DB and forcing a full concurrent backfill — the exact
conditions that produced the bug. All four submissions now match on-chain truth,
and `pending_lifecycle` drains to zero:

```
0x1216aa0dac | claimed | none     | 0x6e6ace4195
0x42c26202f0 | claimed | none     | 0xd11726f8f6
0xa667af211f | claimed | none     | 0xb0ed065841   <- was signed/eligible
0x4b1b9e888f | signed  | refunded | cancel 0x03bc0f4e / refund 0xf73aa83b
```

### L-6 — the everyday launcher ran the signature store UNAUTHENTICATED

**Evidence:** `scripts/run.sh` set no `SIG_STORE_*_TOKEN`; the store logged
`no tokens configured — the API is UNAUTHENTICATED (signatures, claim status and
the allowlist are all world-writable)` on every start.

Finding L-5 introduced scoped bearer tokens and wired them into
`docker-compose.yml`. It did **not** wire them into `run.sh` — the launcher the
README recommends, and the one running this live testnet deployment. So the
control existed in the code and was simply never switched on by the default path.

Anything able to reach the port could deposit signatures, mark transfers claimed,
and edit the allowlist — which is the keeper's *second* enforcement gate.

**Fix:** `run.sh` now generates one random token per role per run
(`openssl rand -hex 32`), exports them so the store and every client inherit them,
and writes them to `$RUN_DIR/tokens.env` at mode 600. Any can be pinned via the
config to survive restarts.

**Verified live:**

```
no token   GET  /submissions     -> 401
no token   POST /allowed/tokens  -> 401
reader tok GET  /submissions     -> 200
reader tok POST /allowed/tokens  -> 401   (readers cannot administer)
```

A transfer then completed end to end through the authenticated stack, and a
keeper started *without* its token failed loudly (`allowlist fetch failed;
skipping tick`) rather than silently degrading — which is the right shape.

### L-7 — `stop.sh` destroyed all bridge history

`run.sh` created the Postgres container with no volume and `stop.sh` did
`docker rm -f`, so every stop/start erased transfer records, refund state,
signatures and indexer cursors.

Harmless with a throwaway anvil — the chain resets too. On a live chain it is
not: the chain remembers and the bridge forgets, and **the signatures do not come
back**, because validators resume from file-based cursors and never re-sign blocks
they already scanned. This destroyed an in-flight refund mid-test: the cancel
attestations vanished, and on restart the keeper (correctly, with no cancel
quorum) claimed a still-valid transfer instead.

**Fix:** a named volume `${PG_NAME}-data`, so `stop.sh` removes only the
container (which holds the port) and history survives.
`bash scripts/stop.sh <config> --wipe` deletes the data when that is genuinely
wanted.

### L-8 — the pool's scan floor was coupled to the scanners'

`run.sh` derived the `--swap` `FROM_BLOCK` from `start_block_for()`, the same
value the validators and indexer use.

Those have different requirements. A scanner floor means "recent history worth
scanning" and legitimately moves forward over time; the pool's token list is
replayed from `TokenListed` logs and its floor must sit **at or before the pool's
deployment, always**. The moment they diverged, the scan began after the listings
and `swapPool` returned a pool with `tokens: []` — a live, well-formed, empty
pool, which is worse than an error because nothing looks wrong.

**Fix:** a separate `SWAP_FROM_BLOCK`, defaulting to the chain floor.

### L-9 — the pool scan chased the tip on every query

Even memoised, a cold cache walked from the pool's deploy block to the tip in one
call: ~2600 blocks at a 10-block cap is 260 round trips **per query**. That
re-triggered the rate limiting the cache existed to avoid, and made a single UI
poll take over a minute.

**Fix:** a fixed budget of 20 chunks per call. Successive polls advance the
cursor, so the backfill still converges far faster than the chain produces blocks
while every individual query stays cheap. The live frontend suite went from
2 failures in 1.2 minutes to **9/9 in 34 seconds**.

### A bug in the L-5 fix itself, caught before it shipped

`park_if_missing` originally keyed off `rows_affected == 0`. That is not the same
as "the row is missing": `mark_cancelled` carries
`AND refund_status <> 'refunded'`, so an already-refunded row matches nothing —
and parking a `cancelled` marker there would later **regress a settled transfer
back to cancelled**, returning it to the refund-candidate list. Now keyed on an
explicit existence check, so a guard that legitimately declined an update is
never mistaken for an absent row.

### Full live functional pass

Beyond the two transfers above, the following was exercised on Sepolia/Hoodi.

**Security invariants** — simulated with `eth_call` against real state, so real
revert data at zero gas. A positive control is included, because a suite where
everything reverts proves nothing:

| # | Attempt | Result |
| --- | --- | --- |
| 1 | re-claim an executed transfer | `AlreadyExecuted` |
| 2 | 1 validator signature (threshold 2) | `NotEnoughSignatures(1, 2)` |
| 3 | 3 signatures vs 2 validators | `TooManySignatures(3, 2)` |
| 4 | non-validator signature alone | `NotEnoughSignatures(0, 2)` — not counted |
| 5 | non-validator + 1 validator | `NotEnoughSignatures(1, 2)` — only the validator counts |
| 6 | **two validators, correct order** | **SUCCESS** (positive control) |
| 7 | two validators, descending order | `InvalidSignerOrder` |
| 8 | non-validator padding a real 2-of-2 quorum | `TooManySignatures(3, 2)` |

Row 8 is finding H-1 on a live chain: junk padding cannot brick a claim, because
the gate refuses on length and the keeper filters to validators before building
the array.

**Two-phase refund**, end to end. Keeper stopped, 2 TST sent, left to strand:

1. indexer flagged it after the timeout — `stuck=true, refundStatus=eligible`
2. validators attested cancel (2/2)
3. keeper restarted → `cancel` on Hoodi, tx `0x03bc0f4e…`
4. indexer observed `Cancelled` → `refundStatus=cancelled`
5. validators attested refund (2/2) → `refund` on Sepolia, tx `0xf73aa83b…`

Sender balance returned exactly (999992e18 → 999994e18), the destination receiver
stayed at **0**, and re-claiming the burned transfer reverts `AlreadyExecuted` —
so it can never be both refunded and claimed. The keeper checks cancel
signatures *before* claim signatures and `continue`s, which is what makes a
cancel quorum win over a still-valid claim quorum.

Also confirmed live: **L-2** — `claim` and `cancel` carry `whenNotPaused` but
`refund` does not, so the circuit breaker cannot trap a victim's funds.

**Same-chain swap**: 100 mUSD → WETH on the live pool, tx `0x6b3fc6bb…`. The
amount received (`31446540880503144` wei) matched the GraphQL quote exactly, and
the indexer recorded it into `swapHistory` with the same figures.

**GraphQL surface**: `chains`, `stats`, `submissions`, `submission`, `history`,
`swapPool`, `swapQuote`, `swapHistory` all exercised against live data.

**`gate-admin send` closes the Solana → EVM direction.** The `["sent", id]`
record PDA has to be derived client-side, which means recomputing the
submissionId exactly as the program does. It uses `bridge_solana::hash`, the
shared implementation Phase 3 locks against the Solidity fixtures — and
deliberately the *no-auto* form, because `native_sender` only enters the hash via
`keccak(nativeSender)` in the auto tail. Using the with-auto form would produce an
id no gate ever derives.

**H5's event protocol works on a real cluster.** The program emitted structured
program data; the relayer decoded it, independently recomputed the submissionId,
matched, and signed. A mismatch is a hard stop, so the signature is proof the two
implementations agree byte-for-byte across VMs.

**Threshold applies per VM, and only relayers sign Solana events.** The EVM
validators scan EVM chains only, so a Solana-origin transfer collects signatures
solely from `solana-relayer` instances. With threshold 2, **two relayers must
run**, each holding a different validator key — one is not enough, and the
transfer simply sits at 1 signature with nothing in any log calling it out.
Second instance added source-only (no `[target]`), which the config already
supports as a valid split.

**Configuration gap, not a code bug: the return leg needs its own
`setLocalToken`.** The first Solana → EVM claim reverted `UnknownAsset`.
`run.sh` wires each chain to the *other* chains' debridgeIds, and the Solana
asset is registered against Sepolia's *own* `debridgeId` (so the outbound claim
resolves). Coming back, Sepolia must also map that id to its local token — which
no EVM-only mesh would ever need. One `setLocalToken` on the Sepolia gate and
both queued transfers claimed on the next tick. `run.sh` has no notion of a
Solana leg, so this step is manual today.

**Decimals do not convert — flag for operators.** The bridge passes raw base
units across VMs unchanged. Sepolia's TestToken is 18-decimal; the devnet mint is
6-decimal, so 5000 wei on the source released 5000 base units (0.005 tokens) on
the destination. That is the hash-bound `amount` doing exactly what it must —
changing it would break the submissionId — but it means a corridor between
mismatched-decimal assets misprices by 10^Δ. Register mints whose decimals match
the source ERC-20, or scale at the edges.

### Solana findings closed this round

**L-4a — receiver-is-a-token-account had no distinct error.** Carried as
`partial` since 2026-08-04: *"the behaviour is correct and deliberate; the
problem is that nothing upstream enforces it"*, with two required deliverables —
a distinct error code and the rule documented in the program header.

`claim` releases funds to the account the validators SIGNED FOR, and an SPL
transfer can only credit a token account, so a **wallet pubkey** — the natural
thing for a user to paste — produces a transfer that can never be delivered. The
gate cannot repair it: the receiver is hash-bound, so substituting the wallet's
associated token account would mean paying an address the validators never
attested, which is exactly the redirection `claim` exists to prevent. So the rule
is enforced, not fixed — but it surfaced as a bare `IllegalOwner`, identical to a
misconfigured vault or the wrong token program, leaving the one *user*-recoverable
failure in `claim` indistinguishable from an operator bug.

**Fix:** `GateError::ReceiverNotTokenAccount` (appended, discriminant 14) via a
`receiver_token_account` decoder used for the two USER-chosen destinations —
`claim`'s receiver and `refund`'s payout account. The vault and the sender's own
account keep the generic decoder, because a non-token vault is a configuration
bug rather than a user error. The rule now has its own section in the module
header, cross-referencing the UI guard that rejects a wallet-shaped receiver
before the user signs.

**Verified live.** Deployed the upgrade to devnet, bridged Sepolia → Solana with
the payer's *wallet* pubkey as receiver, and the relayer's claim failed with
`custom program error: 0xe` — 14, exactly `ReceiverNotTokenAccount`. Three new
predicate tests, including one asserting the code collides with no other gate
error and one keeping it distinct from `BadReceiver` (an authorization failure,
not a typo).

**The compute budget is no longer "unmeasured".** The plan flagged it as
*"unmeasured, flagged for checking, not a finding"*. Measured on devnet against
the deployed program:

```
2-of-2 claim -> 91,303 CU and 91,316 CU   (two independent transactions)
send         -> 26,618 CU
```

At ~25k per `secp256k1_recover` that decomposes as **~42k fixed + ~25k per
signature**, so `total(n) ≈ 42_000 + 25_000n`. That makes the plan's worry real
rather than hypothetical: **a 7-validator gate needs ~217k against a 200k
default**, and without an explicit request every claim, cancel and refund for that
submission fails with nothing naming the cause. `compute_budget_for` already
requested `120_000 + 30_000n`, which covers the model at every set size up to the
~22-validator ceiling; a new test pins the constants against the measurement so
they cannot drift below what the chain actually charges. (The test earned its
keep immediately — it rejected a first estimate of 41k fixed, which undershoots
the measured 91,316 by 316 CU.)

**M-2's two-phase refund now runs on Solana, on-chain.** The instructions had
existed and been account-level tested since 2026-08-04, but neither had ever
executed against a real cluster. `gate-admin` gained `cancel`, `refund` and
`digest`.

`cancel`/`refund` take signatures as **input** rather than producing them. They
are validator attestations over domain-separated digests, and a tool that could
mint them would be a tool that could burn or claw back any transfer; `digest`
prints the bytes to sign so the keys stay wherever they belong.

*Destination burn* — the wallet-receiver transfer from L-4a above, unclaimable by
construction, was cancelled on devnet with a 2-of-2 quorum. Its executed-PDA
marker byte reads **2 (CANCELLED)**, not 1 (CLAIMED), so the two terminal states
stay distinguishable. The relayer then stopped retrying it: 74 attempts before
the burn, zero after — the marker-PDA skip works.

*Source repayment* — a Solana → Sepolia transfer of 777777 units was burned on
its EVM destination, then refunded on Solana. The sender's token account went
498.460767 → **499.238544**, exactly the locked amount returned, and the vault
released precisely that much. Replaying the same refund is refused with
`custom program error: 0x3` (`AlreadyExecuted`) — the `["refunded", id]` marker
holds.

Both directions of the burn-then-repay flow therefore work across VMs: cancel on
Solana for an EVM-origin transfer, and refund on Solana for a Solana-origin one.

**Operational note: the first deploy sizes ProgramData exactly.** The L-4a
upgrade grew the binary from 298,976 to 300,008 bytes and the redeploy failed
with `account data too small for instruction`. `solana program extend <id> 65536`
fixes it, but a deploy pipeline that does not budget headroom will hit this on the
first upgrade that adds a line of code.

### The cross-VM refund is now automatic

Two gaps remained after the manual `cancel`/`refund` proof, and both are closed.

**Nobody attested for Solana destinations.** `crates/validator`'s refund loop
votes only on corridors it can read *both* ends of — correct for it, since it can.
The relayer can read exactly one end, so an EVM → Solana transfer that could not
be delivered had no attester at all: burnable and refundable only by hand, with
the deposit locked until an operator noticed.

New `crates/solana-relayer/src/refund.rs` attests on the **destination** end
only, which is sufficient rather than a compromise — both attestations turn on
destination facts. *Cancel* asks "has the destination NOT paid out"; *refund*
asks "IS the destination burned". Both are readable from Solana. The source-side
checks the EVM loop additionally makes guard against *wasted* attestations, not
loss: the source gate refuses `AlreadyRefunded` and `NotSent` itself. Solana-
SOURCE transfers are deliberately not handled here — their destination is an EVM
chain the EVM validators already attest for. Each attester votes on the end it
can actually see.

`Submitter` gained `try_cancel`, checked BEFORE `try_claim` and `continue`-ing on
success, mirroring the EVM keeper: a burn is the opposite of a payout and must
not queue behind the checks that protect payouts.

**Verified live, end to end, with no manual step.** An unclaimable EVM → Solana
transfer (wallet-pubkey receiver, `0xa44532fb…`):

```
03:59:47  relayer-2  attested cancel
03:59:48  relayer-1  attested cancel          -> quorum
03:59:56  relayer-1  CANCELLED on Solana (burned)
04:00:05  relayer-2  attested refund
04:00:06  relayer-1  attested refund          -> quorum
04:00:14  EVM keeper REFUNDED on Sepolia  tx 0x5cf15c47… (status 1)
```

27 seconds from first attestation to the source being repaid.

**The safety rule earned its keep on live data.** Three transfers sat in the
refund-candidate list; two of them (`0x7aa77a51`, `0x9178a9e6`) had *already been
delivered on Solana*. The DB believed they were stuck because **the indexer does
not observe Solana-side claims** — it only decodes EVM `Claimed` events, so an
EVM → Solana transfer that the relayer delivered still reads as unclaimed and
becomes refund-eligible forever. The attesters read the destination, saw
`executed && !cancelled`, and attested nothing across 90 seconds of ticks. Had
they voted and a peer agreed, the EVM keeper would have refunded transfers that
were already paid out on Solana — a real double-spend. Worth fixing at the source
too: the indexer should decode Solana lifecycle events, which is P2.1's third
bullet and still open.

**Silent under-quorum is now loud.** Solana `Sent` events are signed only by
relayers, so a gate with threshold T needs T relayers with distinct keys. Running
one produced a transfer stuck at 1 signature with nothing anywhere explaining
why. The submitter now reports the requirement at startup — *"gate requires 2
signatures; THIS process contributes 1 — 2 relayers must run, each with a
distinct validator key"* — and warns per-submission when a quorum is short.
`scripts/testing/solana-relayers.sh` launches one instance per key.

### Operational notes

- `stop.sh` removes the Postgres container, so **history does not survive a
  restart**. Worse, it does not come back: validators resume from *file-based*
  cursors, so they never re-sign already-scanned blocks and the `signatures`
  table stays empty for pre-existing transfers. The indexer does rebuild
  `submissions` from chain events.
- Behind a 10-block `getLogs` cap, scanners advance ~1.2 blocks/second
  (10 blocks per 8s poll) against a chain producing 1 per 12s. They gain, but
  slowly: a 1000-block backlog is ~15 minutes. A transfer sent while the scanners
  are still behind is not lost — it simply is not signed until they reach its
  block. Measured on the final test transfer: validator at 11461692, transfer at
  11462720, closing at ~1.2 blocks/s.
- The binding constraint throughout is the free-tier `eth_getLogs` cap. On a paid
  plan or a self-hosted node, raise `MAX_BLOCK_RANGE` and the backfill cost
  collapses — most of the tuning above (poll intervals, chunk budgets) exists to
  live within 10 blocks per request.

## Not addressed

- **M-2/M-3 from the previous round are now closed** — `solana-gate` has
  `Cancel`/`Refund`, and `solana-relayer` is the missing runner. Both are
  covered by account-level tests here.
- **`init` remains untestable** through `solana-program-test` (builtin-dispatch
  conflict); unchanged from the previous round.
- **No SBF toolchain in this environment**, so `cargo build-sbf` and the
  compute-unit measurements R-1 and R-2 reason about were not executed. The CU
  arithmetic behind the cap and the requested budget is stated, not measured —
  it should be confirmed against a real `.so` before deployment. The correctness
  of the cap itself does not depend on it.
- **The signature store still accepts unbounded signature rows per submission.**
  R-1 and R-2 make that harmless to the Solana gate, and H-1 already made it
  harmless to the EVM gate, but a row cap in `bridge-db` would remove the
  griefing surface at its source rather than at each consumer. Recommended as
  follow-up.
